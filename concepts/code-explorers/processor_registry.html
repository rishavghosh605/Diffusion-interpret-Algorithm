How every attention layer gets found and swapped

Nothing on the other four pages in this series tells you where the UNet's attention processors live or how to replace all of them at once. This page is the two methods that do exactly that: walk every submodule, find the ones with attention, and get or set their processor.

How these two methods run

Where it sits in the sampling algorithm

Ho et al. (2020), Algorithm 2, written in the survey's notation. This page has no row: it changes what row 3 means, before the algorithm ever starts.

Calling set_attn_processor before sampling starts changes what every self.attn1 and self.attn2 call inside row 3's \(\epsilon_\theta\) actually computes, for every single iteration of the loop. The algorithm's own notation has no symbol for this: \(\epsilon_\theta\) is treated as one fixed function throughout, but this page is how diffusers lets you swap pieces of it out.

Derive it on paper

The first traces one real dotted name through the recursion. The second is this page's actual point. The third checks what breaks if the two methods' processor counts disagree.

What this means for your project

This is the actual mechanism: pipe.unet.set_attn_processor(your_processor), called once before generation, swaps the processor every cross- and self-attention call in the whole UNet uses, no per-layer code required. A custom processor's __call__ (same shape as AttnProcessor.__call__, the cross-attention page) can read or rewrite hidden_states and encoder_hidden_states at every single attention call, which is a different, much finer-grained intervention point than callback_on_step_end (named on the denoising loop page): that one fires once per sampling step, this one fires once per attention call, dozens of times per step.

Passing a dict instead of one instance (the switch above) lets different layers run different processors: one for the UNet's down blocks, another for its up blocks, keyed by the exact dotted names derivation 1 traces.

Seen whole

A UNet instance goes in on the left; a dictionary mapping every attention layer's dotted name to its processor comes out on the right. Setting runs the same walk in reverse.

Terms on this page

Code terms

Names for places in the code. Each points at exactly one location.

AttentionMixin
A mixin class, not a model on its own. UNet2DConditionModel (the UNet forward, a separate page) inherits from it, which is how every UNet instance ends up with these two methods without defining them itself.
module.named_children()
A PyTorch nn.Module method, not defined on this page: yields each direct submodule once, paired with the name it's stored under. Both recursive functions here call it once per level to walk one step deeper into the tree.
get_processor / set_processor
Methods defined on Attention itself (a separate file, not this page): hasattr(module, "get_processor") (line 51) and hasattr(module, "set_processor") (line 86) are how these functions recognize an attention layer among all the UNet's other submodules (resnets, norms, convolutions) without needing an explicit type check.
fn_recursive_add_processors / fn_recursive_attn_processor
Two closures, one per method, each defined inside the function it belongs to and never used outside it. Both follow the same shape: check the current module, recurse into its named_children, repeat. Derivation 1 traces one full path through this recursion.

Diffusion terms

The ideas the math is built from.

Attention layer (as a tree leaf)
Every self.attn1 and self.attn2 inside every transformer block, inside every down, mid and up block (the UNet forward page), is one leaf this recursion finds. SD 1.5's actual count was not fetched in this environment (network blocked); it depends on how many transformer blocks each cross-attention UNet block contains.
